# Preservation helper reuse boundary audit

The retained direct-helper profile does not admit a cache or persistent Git
process. Exact literal-query reuse is small in this scope, while the original
replacement policy, short-revision resolution and conditional observations remain
observable semantics. This audit closes the immediate exact-key cache hypothesis
without another measurement cohort or an installed runtime change.

## Verified scope and query counts

`preservation_reuse_audit.py` verifies the sealed helper packet, the independent
original source/AST and all nineteen required helper-using case traces. The
current observed helper must erase to the entire original source. Missing frames,
unknown command shapes, altered byte joins or changed packet identity refuse.
The auditor launches no process and performs no Git resolution.

These are argument-shape classifications. They do not attest whether inherited
environment/configuration enabled replacements in the old children. The original
ordinary-Git interface cannot be treated as replacement-disabled in every context.

The seventeen occurrences belong to fifteen repeated queries. This model starts
with an empty shared exact-key cache and keeps every literal revision/path
spelling. It neither expands short IDs nor joins aliases to full IDs or blob
OIDs. Seventeen is a best-case count of redundant literal requests in this
selected helper trace, not observed cache hits or an elapsed-time saving. Other
helpers, earlier warming, concurrent publication and cache contention are outside
that count. Multiplying it by the separate pipe cohort's median would not be a
valid performance estimate.

The earlier seven-loop tree screen found shared blob OIDs across distinct keys.
That separate no-replace capture does not authorize merging the ordinary `show`
queries here: original replacement/config state and short-ID resolution have
not become immutable merely because some selected trees address equal objects.

## Why the obvious startup candidates are not admitted

An ordinary full-revision `show` does not disable replacements. An exact-key
cache can return an old matching body while a fresh original observation would
see changed replacement bytes and reject its source comparison. Independent
old-body pins alone do not repair this lost observation. A before/after equality
check can miss an A–B–A change. New tests make this an explicit logical
countermodel, not a new real-Git or host result. Earlier
[real-Git ref/config and fallback controls](historical-blob-pinned-fallback-result-20261024.md)
remain the separate concrete evidence.

Short revisions must keep their original spelling, resolution and refusal
behavior. A resolved full ID or blob address is not a drop-in cache key. Current
inventory, fixture bytes/attributes and current-file reads remain fresh rather
than being hidden behind historical reuse. Even the correct number of reads is
insufficient if their conditional order changes.

Preplanned batching can load BASE/REVIEWED before an invalid helper has failed;
the original path would not reach either read. A persistent process that issues
requests lazily avoids that particular prefetch but still needs its own proof of
fresh environment/configuration, replacement/ambiguity, errors, stderr, bounds
and retirement semantics. No claim is made that every possible future lazy
protocol must change the conditional schedule.

Consequently, naive exact-key memoization is not selected for this helper.
Object-level reuse, eager batching and a persistent process are not connected.
The installed census adapter's independent pins and unchanged conditional reads
remain intact. Its earlier component pass is not authority to replace a different
ordinary-Git caller or to suppress another caller's stderr/error behavior.

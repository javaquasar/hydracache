# HydraCache 0.73.0 — Evidence-driven performance efficiency

Status: **release candidate; exact-candidate qualification pending**.

0.73 applies six narrowly scoped runtime improvements only after owner attribution, local
falsification, and focused paired qualification. It reduces expiry-scan key copying, shares
immutable event bytes and tags, transfers RESP output buffers without a redundant copy, bounds
HC/2 queued outbound bytes, and caches the durable-store budget total while preserving its
validating public scan. Management overhead produced a measured no-win; allocator work remains
deferred behind an external profiling blocker; retained-byte admission was not applicable.

The Moka removal observer needed by production accounting is supplied by the independently
published, exact-pinned `hydra-moka 0.12.15-hydra.1` package. Its runtime source is byte-equivalent
to the reviewed Git revision, but the registry package is deliberately treated as a new build
identity. HydraCache does not depend on acceptance of the upstream Moka proposal to publish 0.73.

## Compatibility and claim boundary

The runtime changes preserve public APIs, HC/1, HC/2 and RESP bytes, tagged-key and TTL semantics,
tenant isolation, durable record/checksum/fsync formats, Management Center truth semantics, and
same-disk rollback. The real published `v0.72.0` compatibility matrix passed for the earlier
Git-backed candidate; it must be repeated where the final registry-backed identity affects the
receipt.

No numerical performance improvement is claimed yet. Five-pair focused host comparisons passed
the frozen goodput, CPU/op, p99, correctness and resource guards for the earlier exact candidate.
Six-hour run `36278780653` also passed every frozen guard after append-only correction of a
trend-destroying bootstrap implementation, but that evidence is not transferred across the later
Cargo package/source identity change.

## Remaining release gates

Before this note may be changed to `shipped`, the final `0.73.0` source, tree, lockfile, package
metadata, binaries, workload and workflow identities must be frozen. That exact registry-backed
candidate must then pass one six-hour qualification and, only after it passes, one 24-hour
confirmation. Artifacts and nested SHA-256 values must be independently verified and archived;
contract, compatibility, packaging, SBOM, license/advisory, supported-target and release-evidence
gates must be green. Failed attempts remain append-only, and neither duration run authorizes a
portable RSS, allocation, capacity, Redis or Hazelcast comparison.

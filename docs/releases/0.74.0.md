# HydraCache 0.74.0 — RESP throughput and pipeline efficiency

Status: **pre-release draft; no product candidate is accepted or frozen**.

Release 0.74 investigated RESP and native hot paths with matched workloads, explicit native
non-regression guards, and one-hypothesis-at-a-time candidate screening. The investigation has not
yet produced an admissible product change. The published 0.73 runtime therefore remains the
rollback and operational baseline. The controller-resilience work in W11 is opt-in release tooling,
not a product-runtime optimization.

## Compatibility and claim boundary

There is currently no C74 identity and no exact C74 D4 artifact. This draft makes no numerical product-performance,
portable throughput, latency, allocation, capacity, or Redis
superiority claim. Local and host rehearsals are attribution or tooling evidence only. HydraCache
and Redis have different product goals; node-local RESP measurements cannot be presented as
distributed cache capacity or universal product superiority.

No accepted product candidate changes public APIs, RESP/HC wire bytes, durable records, tenant
isolation, authorization, expiration, consistency, durability, backpressure, or configuration.
Product activation is therefore `none`, a product restart is not required, and mixed-version
behavior remains that of 0.73. W11 supervisor and host tooling are separately provisioned and
opt-in; disable and remove that tooling without replacing the 0.73 product binary.

## What the investigation established

The entries below distinguish terminal local decisions from release evidence. They do not combine
multiple hypotheses and do not promote diagnostic measurements into product claims.

| Area | Evidenced disposition | Release effect |
| --- | --- | --- |
| W0–W1 measurement and attribution | Reproducible B73/I74 identities, surface-separated scenarios, workload guards, and local attribution were implemented. | Measurement infrastructure only; non-promotable. |
| W2 RESP input compaction | Rejected by local non-regression screening. | Candidate removed; no product change. |
| W3 response write/flush coalescing | The shallow-tail candidate failed guards; adaptive retry was rejected before measurement because it weakened the backpressure boundary. | Candidates removed; no product change. |
| W4 translation and request metadata | Measured effect stayed below the isolated decision floor. | No product candidate. |
| W5 structured-key materialization | Deferred after the measured effect remained below the decision floor and representation/rollback risk dominated. | No product candidate. |
| W6 client-store contention | W6a was rejected and W6b was not authorized without a measured owner. | No concurrency change. |
| W7 multi-key dispatch | The DEL candidate failed the native guard; same-binary noise remained unresolved. | Candidate removed; atomicity unchanged. |
| W8 validation and ownership | W8a failed the tail guard; W8b had no compatible candidate. | Candidate removed; authorization/public API unchanged. |
| W9 runtime follow-ups | Atomic ordering had no isolated CPU win; buffer reuse and durable group commit were not authorized; scheduler work confirmed an existing owner; Linux allocator profiling found no admissible candidate. | Platform defaults, durability, and the system allocator remain unchanged. |
| W10 composition | No proposal was accepted, so composition was not attempted and C74 could not be frozen. | No product candidate. |
| W11 long-run controller | Local tests and bounded non-product host rehearsals established fail-closed lifecycle, lease, process-identity, checkpoint, and controller-loss behavior. A 20-attempt role-overhead rehearsal stayed inside its frozen asymmetry and supervisor resource ceilings. | Tooling evidence only; product qualification and release admission remain open. |

The role-overhead rehearsal used non-product fixtures. Its measured medians and ceilings are retained
in the machine-readable W11 evidence, but they are not claims about HydraCache request throughput,
latency, allocation behavior, or Redis-relative performance.

## Activation and rollback

No 0.74 product optimization is active by default because no candidate has been accepted. Continue
running the published 0.73 product runtime. If W11 tooling has been installed for qualification,
stop and disable `hydracache-performance-supervisor-074.service`, remove only the separately
provisioned 0.74 supervisor/qualification assets, and verify the 0.73 product service independently.
Do not reuse host-local campaign state as release evidence.

Any future accepted candidate must document its input/output/store memory bound, wire/durable/API
and configuration impact, oldest compatible reader and writer, mixed-version behavior, emergency
disable path, old-binary rollback, and the evidence invalidated by source or dependency changes.

## Remaining admission work

The opt-in production RESP client-certificate policy has local semantic proof;
the scheduled RESP2/3 adapter now uses that real factory/accept loop and AUTH on
each connection. This security prerequisite is not an accepted performance
optimization. Separate allocation-only diagnostics cover requested System
layouts, process RSS and logical delete/refill ownership; unavailable allocator
active/resident/retained is explicitly not a passing retention gate. Neither
addition closes full D3/native numerical admission or resolves C74.

Release admission remains fail-closed until all of these are complete on one exact frozen C74:

- resolve and freeze candidate source identity, admitted host, qualification runner, and exact Redis
  server/client binary digests;
- receive explicit authorization before any product candidate, same-box Redis, six-hour, or 24-hour
  workload is launched;
- pass separate RESP, native HC/1, native HC/2, ClientSurfaceState, and embedded HydraCache guards,
  plus integrated interaction and compatibility cells;
- complete controller overhead qualification and the authorized six-hour and 24-hour campaigns;
- produce exact package, supported-target, SBOM, advisory, and license receipts;
- retain immutable raw manifests, controller history, complete I74/C74 packets, outer and nested
  SHA-256 verification, and a downloadable source-of-record archive;
- rerun release-scoped expected-red canaries and all final admission checks on the exact candidate
  commit.

Until those gates pass, `performance-contract-check --require-ship` and
`release-evidence --require-ship` must remain red.
